# 04 — chat-bot OTA 与启动恢复

**优先级：** P1。  
**依赖：** 03 的最小 A/B OTA 已在相同芯片完成；若任务目标要求语音 chat-bot，另依赖 01/02。硬件队列排在 AC791 语音和 OTA 最小包之后。

## 目标与当前证据

确认目标 chat-bot 工程在真实升级包格式、flash bank 与设备 RAM/flash 条件下是否能够 OTA，并测量失败/掉电后的启动和恢复行为。不能默认“缩减功能”是解决办法；先给出尺寸来源与产品需求权衡。

历史记录中的 AC792N chat-bot 约 2.46 MiB、单 bank 约 1.42 MiB、vendor package 上限 `0xF0000` 都不是当前验收数据。任务执行时须在新 root / 当前 canonical pin 实际构建、读取 flash map、生成 package 后重测；package 头/目录、资源分区和下载限制都计入。AC79/AC792 各板布局单独核实，不把未验证尺寸带入是否可 OTA 的结论。

## 允许修改范围

- 可新增测量脚本/报告或隔离 OTA 配置；若需改产品代码，应先列出变更和目标验收，不得静默删除 UI、语音、网络或模型功能来挤进 bank。
- 可修改产品 OTA/error recovery glue，仅限明确派发范围；禁止默认改变应用 bank、TuyaOpen/KV/UF 分区。
- 外部云端固件上传、灰度/发布需本次派单明确授权。首次切换 bank layout 或重刷必须属于派单范围；确认并保留配网/授权信息，不默认擦除用户数据。

## 步骤与验收

1. 用目标芯片、目标 board config 和相同工具链构建当前 chat-bot；逐项记录 `dist` 文件、裸镜像、资源总量、链接 map、vendor OTA 包大小、header 开销和 bank/adapter ceiling。
2. 若超限，报告超限量和各资源来源，列可选产品方案与影响；不自动做功能裁剪。
3. 只有确认尺寸可装且完成 03 最小 OTA 后，生成一份完整 vendor OTA 包，在测试设备做 A→B，并验证新固件启动、cloud reconnect、TTS/UI、版本上报、KV/license/provisioning 保留。
4. 检查下载中断、包损坏、verify fail、boot-info 写失败/超时、第一次新 bank 启动失败及升级后断电。记录 vendor bootloader 的真实选择/回退行为；恢复机制未被测到时写“未知”。
5. 若本次派单明确包含首次切换分区/重刷，先备份并验证配网/授权信息保留方法，再按派单操作；否则不做该操作。设备必须能按预案回到已知可启动状态；记录刷机救援步骤和保留区影响。设备恢复后再交还。

**通过条件：** 真实产物含完整 vendor package 后同时低于物理 bank、`0xF0000` adapter ceiling，并通过 cloud-to-device upgrade；新版本启动和用户数据保留经验证；中断/失败恢复有可复核结果。不能达成时明确为容量/可靠性 blocker，不宣传 OTA ready。

## 停止条件与交付

尺寸越界、bank map 不明、包格式/校验未知、无恢复途径、设备数据可能丢失时停止。交付文件 SHA、尺寸表、构建配置、升级日志、断电/坏包结果、恢复指引、尚未验证项。

## 共用规则

遵循 `README.md` 的隔离与硬件独占规定；先通过 00 和 03。主仓/平台仓 dirty 分别保护；串口现场核实，不用其他项目 COM21。实机队列一位操作者，明确交接。任何上传/发布/远端写都需额外授权。
