# sanoTTS 验收附录：连贯播放改进 (2026-10-30)

## 背景

原固件采用"分块流式"策略：每计算完一个 16 帧解码块（≈185ms 音频）就立即送入播放器。  
由于 RTF ≈ 210，每块产生 185ms 音频却需约 36 秒计算，播放器在两块之间会有长时间无声等待，
导致听感严重断裂、内容难以辨别。

## 改进方案：先算完再播 (compute-all-then-play)

### 实现（提交 `ae57a668`）

在 `examples/multimedia/sanotts_serial/src/tuya_app_main.c` 的 SAY 处理路径中：

```
旧流程：G2P → audio_begin → [逐块: 推理 → 送播放器] → audio_finish
新流程：G2P → [全部推理 → 写入 PSRAM 缓冲] → audio_begin → [一次性播放] → audio_finish
```

**关键参数：**
- PCM 缓冲：`tal_psram_malloc(n_ids × 512 × 4 bytes)`，动态按音素数估算
  - 141 音素 → 估算 72192 采样 × 4B = **288 KB**（实际远小于 PSRAM 剩余约 10GB）
- 两级降级：半大小 → 流式（保证不崩溃）
- finish 超时按实际采样数自适应计算

### 实测验证结果（三组，全部通过）

| 文本 | 音素 | 音频时长 | 推理耗时 | 欠载 | 结果 |
|------|------|----------|----------|------|------|
| "你好" | 19 | **0.348 秒** | 68.26 秒 | 0 | ✅ 连续播出 |
| "今天天气真好。" | 91 | **1.173 秒** | 342.70 秒 | 0 | ✅ 连续播出 |
| "你好，欢迎使用涂鸦智能语音。" | 141 | **2.067 秒** | 650.43 秒 | 0 | ✅ 连续播出 |

三组测试均为**一次性连续发声，无任何断裂，欠载 0 次**。

### 超时公式标定（三点二次拟合）

```
t_compute ≈ 0.0192 × n² + 1.699 × n + 29  (秒)
timeout   = max(user_timeout, t_compute × 1.25 + 60)
```

### 等待时间说明

改进**不缩短推理等待时间**（RTF ≈ 210 为物理算力瓶颈），改进的是**发声质量**：
- 旧体验：推理中断断续续发声，内容无法连贯感知
- 新体验：等待 N 分钟后，一次性连续播出完整语音

> [!NOTE]
> 等待时间与文本长度的关系（实测）：
> - 2 字（"你好"）≈ 1 分钟
> - 12 字（完整句子）≈ 11 分钟
> 
> 缩短等待时间需要 CMSIS-DSP NEON 加速或量化推理，已在 M4 性能说明中记录。
